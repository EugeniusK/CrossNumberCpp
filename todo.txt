ACTION 1: Single-Statement Block Unboxing & Block Flattening  [COMPLETED]
--------------------------------------------------------------------------------
Status: COMPLETED & VERIFIED (Instruments trace: self-weight dropped 504ms -> 205ms, total 2.59s -> 1.14s)

Problem:
  Every `{ ... }` block in clue scripts is parsed as a BlockStmtNode.
  For example, in `if (cond) { output[i] = 1; }`, the `then_branch` points to a
  BlockStmtNode containing exactly 1 child statement (`OutputIndexAssignStmtNode`).
  Executing this incurs:
    1. Virtual call: IfStmtNode::execute
    2. Virtual call: raw_cond_->evaluate(env)
    3. Virtual call: BlockStmtNode::execute
    4. Loop overhead: `for (size_t i = 0; i < 1; ++i)`
    5. Virtual call: OutputIndexAssignStmtNode::execute
  This results in 4 virtual function calls for a single array write.

Implementation:
  - In `BlockStmtNode::resolve_slots` (or an AST rewriting helper `resolve_stmt`):
    If `owned_statements_.size() == 1`, unwrap it and return the single
    `std::unique_ptr<StmtNode>` directly to the parent node.
  - In `IfStmtNode`, `ForStmtNode`, `WhileStmtNode`:
    When resolving body/then/else branches, if the child is a BlockStmtNode with
    1 statement, unwrap it to point directly to the inner statement.
  - If a BlockStmtNode contains nested BlockStmtNodes, flatten them inline into a
    single flat statement list so the outer block iterates directly without recursion.

ACTION 2: Canonical For-Loop Specialization (ForCountStmtNode)  [COMPLETED]
--------------------------------------------------------------------------------
Status: COMPLETED & VERIFIED (Instruments trace: ForStmtNode eliminated; ForCountVarLimitStmtNode 108ms self)

Problem:
  Clue scripts frequently use canonical integer counting loops:
    `for (let i = 0; i < OUTPUT_ARRAY_LENGTH; i = i + 1) { ... }`
  In `ForStmtNode::execute`, each iteration performs 3 virtual dispatches:
    1. raw_cond_->evaluate(env)
    2. raw_body_->execute(env)
    3. raw_update_->execute(env)
  Across large iteration spaces (up to 10,000 items), millions of virtual calls
  are made just to increment and test loop counters.

Implementation:
  - During `ForStmtNode::resolve_slots`:
    Inspect the loop shape:
      * `init`: AssignStmtNode / VarDeclNode initializing counter `var_slot` (e.g. 0).
      * `condition`: `BinaryExprVarOpNode<Less>` or `BinaryVarVarOpNode<Less>` comparing
        `var_slot < limit_slot` (or literal limit).
      * `update`: AssignStmtNode incrementing `var_slot = var_slot + 1`.
  - When matched, replace `ForStmtNode` with a specialized `ForCountStmtNode`:
    ```cpp
    class ForCountStmtNode : public StmtNode {
      int var_slot_;
      int limit_slot_;
      int init_val_;
      std::unique_ptr<StmtNode> body_;
      StmtNode* raw_body_ = nullptr;
    public:
      void execute(Environment& env) override {
        int limit = env.get_slot_value(limit_slot_);
        for (int i = init_val_; i < limit; ++i) {
          env.set_slot_value(var_slot_, i);
          raw_body_->execute(env);
        }
      }
    };
    ```
  - Result: Eliminates condition and update virtual calls completely (2 of 3 virtual
    calls removed per iteration), running counter checks at native CPU speed.

ACTION 3: AssignStmtNode Specialization (AssignLit, AssignVar, AssignOpSelfLit) [COMPLETED]
--------------------------------------------------------------------------------
Status: COMPLETED & VERIFIED (Specialized AssignLitStmtNode, AssignVarStmtNode, AssignOpSelfLitStmtNode<Op>, AssignExprStmtNode)

Problem:
  `AssignStmtNode::execute` currently executes a chain of 3 runtime conditional branches:
    ```cpp
    if (slot_ < 0) [[unlikely]] ...
    if (expr_is_lit_) env.set_slot_value(slot_, expr_lit_val_);
    else if (expr_slot_ >= 0) env.set_slot_value(slot_, env.get_slot_value(expr_slot_));
    else if (raw_expr_) env.set_slot_value(slot_, raw_expr_->evaluate(env));
    ```
  Hot assignments inside loops (`k = k + 1`, `mult = mult * 10`, `a = b`, `stop = 1`)
  constantly branch through this ladder.

Implementation:
  - Specialize `AssignStmtNode` at resolve time (`resolve_slots`) into concrete subclasses:
    1. `AssignLitStmtNode`:
       `void execute(Environment& env) override { env.set_slot_value(slot_, val_); }`
    2. `AssignVarStmtNode`:
       `void execute(Environment& env) override { env.set_slot_value(dst_, env.get_slot_value(src_)); }`
    3. `AssignIncrStmtNode` (for patterns like `k = k + 1`):
       Directly increments `env.set_slot_value(slot_, env.get_slot_value(slot_) + step_);`
       bypassing expression evaluation completely.
    4. `AssignExprStmtNode`: Fallback for general expressions.

ACTION 4: FunctionCallNode Argument Caching & Specialization  [COMPLETED]
--------------------------------------------------------------------------------
Status: COMPLETED & VERIFIED (FunctionCallVar1Node specialized; argument slots and literal values cached; constant builtins folded)

Problem:
  Builtin calls (`dsum(i)`, `get_nth_digit(i, 2)`, `is_prime(i)`, `is_palindrome(i)`)
  evaluated arguments via virtual dispatch: `args_[0]->evaluate(env)`.
  When `args_[0]` was a `VariableNode`, this invoked a polymorphic method just to read
  `env.get_slot_value(slot)`.

Implementation:
  - In `FunctionCallNode`, resolved argument slot IDs and literal constants at `resolve_slots`:
    Cached `int arg_slots_[4]`, `bool arg_is_lit_[4]`, and `int arg_lit_vals_[4]`.
  - Added inline argument evaluator `get_arg(i, env)` that reads slots or literal values
    directly, falling back to `args_[i]->evaluate(env)` only for complex expressions.
  - Specialized high-frequency 1-argument slot functions (`is_prime(i)`, `dsum(i)`,
    `is_palindrome(i)`, `isqrt(i)`, `reverse(i)`) into `FunctionCallVar1Node<Fn>`,
    evaluating `env.get_slot_value(slot)` with zero virtual calls and zero switch branches.
  - Folded constant builtins with all-literal arguments at parse/fold time into `LiteralNode`.

ACTION 5: IfStmtNode Devirtualization & ForCount-If Fusion  [COMPLETED]
--------------------------------------------------------------------------------
Status: COMPLETED & VERIFIED (IfThenStmtNode implemented; ForCountIfVarLimitStmtNode and ForCountIfLitLimitStmtNode specialized)

Problem:
  1. In `src/ast.cpp`:
     `if (raw_cond_->evaluate(env) != 0) { then_branch->execute(env); }`
     Notice it called `then_branch->execute(env)` (dereferencing `std::unique_ptr`)
     instead of using the cached `raw_then_->execute(env)`.
  2. The majority (>95%) of `if` statements in clue scripts have NO `else` branch
     (`else_branch == nullptr`). The `else if (raw_else_)` branch was checked on
     every false condition.
  3. Millions of `if` executions occur as loop bodies inside canonical counting loops.

Implementation:
  - Ensured `raw_then_->execute(env)` is called directly via cached raw pointer with `[[likely]]`.
  - Specialized `IfStmtNode` into `IfThenStmtNode` (when `else_branch == nullptr`) to completely
    eliminate the `raw_else_` check on false conditions.
  - Fused canonical counting loops with `IfThenStmtNode` bodies into `ForCountIfVarLimitStmtNode`
    and `ForCountIfLitLimitStmtNode`: evaluates condition and invokes `raw_then_->execute(env)`
    directly inside the native C++ loop, completely eliminating the intermediate `IfStmtNode::execute`
    virtual call per loop iteration.

ACTION 6: WhileStmtNode Canonical Loop Specialization  [COMPLETED]
--------------------------------------------------------------------------------
Status: COMPLETED & VERIFIED (Specialized WhileVarLitCondStmtNode, WhileVarVarCondStmtNode, WhileVarSquareVarLimitStmtNode, WhileVarSquareLitLimitStmtNode, WhileVarCondStmtNode, WhileVarModVarZeroStmtNode; 2-statement body direct bypass; small block unrolling)

Problem:
  In clue scripts, `while` loops execute millions of iterations in multiple hot patterns:
  1. Sentinel loop: `while (stop == 0) { ... }`
  2. Numerical reduction / stepping loop: `while (temp > 0) { ... }` or `while (t < OUTPUT_ARRAY_LENGTH) { ... }`
  3. Squared bound search: `while (k * k <= i) { ... }` (in d37) or `while (i * i < OUTPUT_ARRAY_LENGTH) { ... }`
  4. Prime factor reduction: `while (n % p == 0) { ... }`
  Previously, every iteration dispatched 2 virtual calls (`raw_cond_->evaluate` and `raw_body_->execute`).
  For `k * k <= i`, condition evaluation also incurred inner virtual dispatch to `Multiply`.

Implementation:
  - In `WhileStmtNode::resolve_slots`:
    Pattern-matches condition into concrete template subclasses:
    1. `WhileVarLitCondStmtNode<Op>`: checks `eval_binary_op_static<Op>(env.get_slot_value(slot), lit_val)` directly.
    2. `WhileVarVarCondStmtNode<Op>`: checks `eval_binary_op_static<Op>(env.get_slot_value(left_slot), env.get_slot_value(right_slot))` directly.
    3. `WhileVarSquareVarLimitStmtNode<Op>`: directly checks `var * var <= limit` using native integer multiplication and comparison.
    4. `WhileVarSquareLitLimitStmtNode<Op>`: directly checks `var * var < lit`.
    5. `WhileVarModVarZeroStmtNode`: checks `num % div == 0` directly.
    6. `WhileVarCondStmtNode`: checks `env.get_slot_value(slot) != 0` directly.
  - In `WhileBaseStmtNode`:
    When body is a 2-statement `BlockStmtNode`, caches `raw_stmt0_` and `raw_stmt1_` and invokes
    them directly, completely bypassing the intermediate `BlockStmtNode::execute` virtual dispatch.
  - In `BlockStmtNode::execute`:
    Directly unrolls blocks of size 2, 3, or 4 to eliminate iteration loop overhead.

ACTION 7: Fused While/Modulo-Zero Specialization for Clue d37 (WhileSquareFreeStmtNode / IfVarModSquareZeroStmtNode)
--------------------------------------------------------------------------------
Hotspots:
  - IfThenStmtNode::execute (117 ms self, 351 ms total)
  - WhileVarSquareVarLimitStmtNode<Op 8>::execute (93 ms self, 367 ms total)
  - BinaryExprLitOpNode<(BinaryOp)5>::evaluate (64 ms self, 118 ms total) [i % (k * k) == 0]
  - BinaryVarExprOpNode<(BinaryOp)4>::evaluate (45 ms self, 67 ms total)  [i % (k * k)]
Estimated Gain: ~180 – 250 ms

Problem:
  Clue d37 executes for all candidates during domain shaking and cell assignment:
    ```js
    while (k * k <= i) {
      if (i % (k * k) == 0) { is_sq_free = 0; }
      k = k + 1;
    }
    ```
  Currently:
  1. `WhileVarSquareVarLimitStmtNode` runs the while condition (93 ms self).
  2. Each iteration calls `raw_stmt0_->execute` -> `IfThenStmtNode::execute` (117 ms self).
  3. Inside `IfThenStmtNode`, `cond->evaluate` dispatches polymorphically:
     - `BinaryExprLitOpNode<Equal>` (64 ms self)
     - `BinaryVarExprOpNode<Modulo>` (45 ms self)
     - `BinaryVarVarOpNode<Multiply>` (`k * k`)
  4. Each iteration calls `raw_stmt1_->execute` -> `AssignOpSelfLitStmtNode<Add>::execute`.
  This accounts for over 350 ms of CPU time in nested virtual dispatch and `%` calculations.

Implementation:
  - Option 1 (Fused While Loop): Detect when a while loop has the canonical pattern:
    Condition: `var * var <= limit`
    Statement 0: `if (limit % (var * var) == 0) flag = 0;`
    Statement 1: `var = var + 1;`
    Fuse into a single concrete node `WhileVarSquareModZeroStepStmtNode` executing the entire loop in native C++!
  - Option 2 (Specialized Condition Node): Specialize `BinaryOpNode` when left is `var1 % (var2 * var2)` and right is `0`
    into `BinaryVarSquareModZeroOpNode`, avoiding intermediate binary op allocation and virtual calls.

ACTION 8: ForCount Loop Specialization for Builtin Comparisons (ForCountIfFnVarLimitStmtNode)
--------------------------------------------------------------------------------
Hotspots:
  - ForCountIfVarLimitStmtNode::execute (121 ms self, 266 ms total)
  - BinaryExprExprOpNode<(BinaryOp)11>::evaluate (40 ms self, 76 ms total) [LogicalAnd in d24]
Estimated Gain: ~50 – 80 ms

Problem:
  In clue a17:
    `for (let i = 0; i < OUTPUT_ARRAY_LENGTH; i = i + 1) if (dsum(i) == c3) output[i] = 1;`
  In clue d24:
    `for (let i = 0; i < OUTPUT_ARRAY_LENGTH; i = i + 1) if (is_prime(i) && dsum(i) == c4) output[i] = 1;`
  Both clues re-evaluate dynamically whenever clue dependencies `c3` or `c4` are modified.
  `ForCountIfVarLimitStmtNode` iterates 10,000 times and makes a virtual call to `raw_cond_->evaluate(env)`
  on every iteration (10,000 virtual calls per clue execution).

Implementation:
  - In `ForStmtNode::resolve_slots`:
    When `cond` is `FnCall1VarVarOpNode<Fn, Op>` where `fn_slot == loop_var_slot`:
    Specialize to `ForCountIfFnVarLimitStmtNode<Fn, Op>`:
    ```cpp
    int limit = env.get_slot_value(limit_slot_);
    int rhs = env.get_slot_value(right_slot_);
    for (int i = init_val_; i < limit; ++i) {
      if (eval_binary_op_static<Op>(dsum(i), rhs)) {
        raw_then_->execute(env);
      }
    }
    ```
    Eliminates all 10,000 virtual condition calls per loop execution.

ACTION 9: Assign Specialization for Single-Argument Function Calls (AssignFnCall1VarStmtNode)
--------------------------------------------------------------------------------
Hotspots:
  - AssignExprStmtNode::execute (50 ms self, 80 ms total)
Estimated Gain: ~20 – 35 ms

Problem:
  In clue d37:
    `let s = dsum(i);`
  AssignStmtNode currently only specializes `AssignLit`, `AssignVar`, and `AssignOpSelfLit`.
  Assignments from function calls (`s = dsum(i)`) fall back to `AssignExprStmtNode`, incurring
  a virtual call to `raw_expr_->evaluate(env)` for every iteration of the outer for-loop.

Implementation:
  - In `AssignStmtNode::resolve_slots`:
    If `expr` is a single-variable builtin function call (`is_fn_call_var1`), specialize to:
    ```cpp
    template <BuiltinFn Fn>
    class AssignFnCall1VarStmtNode : public AssignStmtNode {
      int slot_;
      int arg_slot_;
    public:
      void execute(Environment& env) override {
        env.set_slot_value(slot_, eval_builtin_1<Fn>(env.get_slot_value(arg_slot_)));
      }
    };
    ```
